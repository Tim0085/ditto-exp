# 代码导读

按“一题是怎么跑的”顺序读。

## 1. 一格：`scripts/real.sh` → `scripts/run.sh e2e` → `src/run.ts`

- `real.sh run full-s4` 按计划依次跑各格。每格调 `run.sh e2e <格子> <布局> <核> ...`：先按布局起被拆出的 Worker 容器（`src/worker-server.ts`，官方 `createWorkerHttpHandler`），再起编排器容器跑 `src/run.ts`。所有被测容器绑在同 2 个核上，在不能出外网的 Docker 网络里；模型请求都发给出口容器。
- `run.ts`：读题，按布局建 Ditto 运行时（`createDitto`）——本进程的 Worker 直接登记，被拆出的经官方 HTTP 传输登记为远端（`registerRemote`）；Direct 不建运行时（见第 3 节）。37 条“车道”同时取题，每题一次 `runOne`。前 20 题做完时取第一次读数、最后一题派出时取第二次，两次之间是稳态窗口（吞吐、各进程主线程忙多久都在窗口里算）。最后写 `<格子>.json` 和两个附加文件（第 5 节）。

## 2. S4 的一题：`src/app.ts`

- `s4Plan` 是官方写法的 loop：每一步一个小 graph，用 `graphStep` 顺序执行。每段历史对话：`CONTEXT.UPDATE`（追加）→ `CONTEXT.SELECT`（purpose memory，挑出用户消息）→ `MEMORY.WRITE` → `CONTEXT.COMPRESS`（压回 32K）。提问：`INFER.REASONING.SAMPLE`（检索词）→ 每个检索词一次 `MEMORY.SEARCH` → `CONTEXT.UPDATE`（问题和检索到的记忆经 ingress 进来）→ `CONTEXT.SELECT`（purpose infer）→ `INFER.REASONING.SAMPLE`（LongMemEval 官方回答模板）。
- 每一步交给 Worker 的入参由 `loadInput`、`updateInput`、`keywordInput`、`answerInput` 等函数拼出，graph 和 Direct 共用。`renderHistory` 把挑出的条目按 LongMemEval 官方格式排成历史。
- Worker：`contextWorker`（官方 CONTEXT，放开条数和单条大小两个上限）、`memoryWorker`（官方 SQLite 记忆，多用户按命名空间隔开）、`inferWorker`。官方存储适配器从 `official/`、`relaxed/` 引用（`scripts/fetch-official.sh` 取）。
- 提示词和真实模型的开关在 `src/common.ts`（`MEMCTX_REAL=1` 用真实模型那一套）。

## 3. Direct：`src/direct.ts`

同样的步骤写成普通函数：`createContext`、`createMemory`、`createInfer`（provider 由官方 `createRuntimeServices` 从同一份配置建），rag 的工具经官方 `ToolRegistry.call`、检索经 `createRetrieval`。`createDirectS4().run` 和 `s4Plan` 一一对应；`createDirectRag().run` 和官方 `runRagPlan` 一一对应（提示词逐字复制，测试核对），并按官方的图名报每一步的开始、完成、出错，失败分类和 Monolithic 一样。

## 4. rag 的一题：官方 `rag-a/examples/patterns/rag-qa/index.ts` + `src/rag.ts`

- `run.ts` 调官方 `runRagLoop`（和官方 `runRag` 一样经 `runtime.loop`）。官方示例是一题一个运行时；实验要几十题同时跑，所以 `rag.ts` 的 `RagDispatch` 把 INTERACTION 的 4 个工具和 RETRIEVAL 的检索按题转给这一题自己的官方 `RagAdapters`。
- `ragAnswerText` 把官方报告转成判分用的文字；`ragFailKind` 把失败分成“模型输出过不了官方检查”（按答错计）和“程序或网络出错”。
- 数据：`src/rag-sources.ts`（一段对话一个来源）、`src/prepare-rag.ts`（写题目和知识文件）、`src/build-rag-store.ts`（写进官方 SQLite 记忆库）。

## 5. 测量和记录

- `src/stats.ts`：一次读数（主线程忙的时间、CPU、内存、容器的 CPU 和内存）；两次读数之间的差。
- `src/calls.ts`：每次调用的原始用时（节点名、开始时刻、用时、题的序号、本进程执行还是经 HTTP 的往返）。编排器、被拆出的进程（`worker-server.ts` 的 `/stats/calls`）、Direct 都记。写进 `<格子>.calls.json.gz`。
- `run.ts` 每 5 秒取一次各进程的读数（`samples`）；rag 每题完整的官方报告写进 `<格子>.reports.jsonl.gz`。
- `src/run_info.py`：每轮开跑时记下程序摘要、版本、镜像、主机、数据摘要和计划（`run-info.json`）。

## 6. 出口：`src/egress.ts`

唯一能上外网、拿到 DeepSeek 密钥的进程。认题和步骤（S4 用内部标记，rag 认官方提示词）、去掉标记、加防缓存编号、关闭思考；发之前按最坏情况预扣，收到回复按用量结算，超过上限就不发；临时故障重试；账本、每个请求、完整请求体（去重）、完整回复都记下来。

## 7. 判分和汇总

- `src/judge.py`：GPT-4o 按 LongMemEval 官方提示词判分（同一题相同的回答只判一次，可断点续判）；逐题配对比较（Agresti–Min 区间、符号检验），拆开对 Monolithic、各布局对 Direct、同一布局跑两次。
- `src/export.py`：每格一行（吞吐、用时分位、各进程资源、请求是否和 Monolithic / Direct 逐字相同）、成对比较。吞吐有两种算法：两点法，和把窗口起点在一整波里各取一次再合起来的整波平均；`src/real_report.py`：`report.md`；`src/real_detail.py`、`src/rag_detail.py`：详细分析；`src/workbook.py`：Excel。

## 8. 其余

- 数据准备：
  - `src/prepare.ts`；
  - `src/sample.ts`：固定顺序。`--seed 42 --out <目录>` 写种子 42 的数据；不带参数是更早几轮用的种子 20261119；
  - `src/sample500.ts`：全量 500 题，前 200 题和同一种子的前 200 题逐字节相同；
  - `src/build-store.ts`：S4 的背景记忆库。

  这些程序写文件都经过 `common.ts` 的 `writeNew`：文件已经存在时，内容相同就不重写，内容不同就报错，不会覆盖已有的数据。
- 种子对照：`report/seed_compare.py`，把两个种子下 rag 那一轮的结果放在一起，按跑之前写定的两条判据下结论。
- 低并发组：`report/low_criteria.py`，按跑之前写定的判据下结论：负载够不够低、拆开的吞吐收益、扣除模型快慢以后的收益、正确率。只读结果，写 `判据.md`、`判据.json`。
- 全量实验：`report/full_criteria.py`，按跑之前写定的口径出结论表：吞吐的主数用整波平均的两轮合并，正确率只取拆开对 Monolithic 的单轮比较、单独做 Holm 校正。只读结果，写 `结论.md`、`结论.json`。
- 阶段汇报：`report/build_report_1121.py`，11-21 汇报的结果表格（18 张，每张第 1 行是合并到表宽的注释）和图（3 张，图里不写图号和图名）：全量实验为主，附低负载对照和离线并发扫描。只读结果；吞吐收益和 `结论.json` 逐一核对，正确率配对从每题判分重算、和 `accuracy.json` 核对，对不上就停。数值按十进制四舍五入。
- 离线并发扫描：
  - `scripts/sweep.sh`：按计划一格一格跑，每格 200 + 并发 道题；有验收、续跑、补测、超时作废；
  - `src/sweep_report.py`：汇总和判断，吞吐用“整波平均”来判断，两点法照列；
  - `src/cell_check.py sweep`：按题核对，只要几格都含同一道题，这道题每一步的请求、结果和报告都要逐字相同。
- 假模型：`src/fake-model.ts`、`src/rag-fake.ts`（离线演练和测试用，回复过得了官方检查）。
- 以前的离线测量（单题测量、排队推算、端到端）：`src/estimate.py`、`src/report_tables.py`、`scripts/phase*.sh`。
